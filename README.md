# Harlan 的第二大脑 · 使用手册

> 这份文件是**写给你（人类）**的操作手册：你每天该做什么。
> `AGENTS.md` 是**写给 LLM Agent** 的规则书：它该怎么维护这个库。
> 两者冲突时，**以 `AGENTS.md` 为准**。

## 一句话

你负责投递来源和提问，Agent 负责其余全部维护工作。

## 核心循环

> 投递 → 摄入 → 讨论 → 验收 → 提问 → 落盘 → 体检 → 回到投递

## 投递：三种东西，三条路

| 你手上的东西 | 放到哪 | 说明 |
| --- | --- | --- |
| 外部资料：文章、官方文档、PDF、报错原文 | `raw/`（或 `raw/assets/`） | 浏览器剪藏用 Obsidian Web Clipper，目标目录设成 `raw/` |
| **你自己的排障记录、学习笔记、方案设计** | `raw/personal/` | 走**另一条流程**：不与外部来源混算，结论会标成「个人经验」 |
| 一段代码、一个命令 | 先写进 `raw/personal/` 的一个 md | Agent 会把它整理成 `howto/` 页面 |

**外部资料和你的记录必须分开放**，因为处理方式不同：前者是"提炼事实"，后者是"记录你的判断"。混在一起，你的观点就会被自己的文章反复背书。

## 你常说的四句话

在 Codex 里打开这个库，然后：

| 你说 | Agent 会做 |
| --- | --- |
| **「摄入 raw 里的 xxx」** | 读来源 → 先汇报要点问你强调什么 → 写摘要页 → 更新概念/实体 → 如有操作内容则写 `howto/` → 更新 index 与 log |
| **「问：xxx」** | 先读 index 定位 → 结合多页作答并给出处 → **把结论写成 `outputs/` 页面**（不会只留在对话里） |
| **「我想搞清楚 xxx」** | 记进 `QUESTIONS.md` 的待解决队列，之后摄入来源时自动回头检查是否已回答 |
| **「体检一下」** | 跑 `scripts/lint.py` + 语义检查，输出体检报告到 `outputs/` |

其中「落盘」这一条值得强调：**任何有价值的分析都会变成库里的一个页面**，而不是消失在聊天记录里。这决定了你的探索能不能积累。

## 手动命令

```bash
cd ~/learn/codex知识库/Harlan的第二大脑

# 一次性：初始化版本历史（Agent 无权创建 .git 目录，需要你手动跑一次）
git init && git add -A && git commit -m "初始化第二大脑"

# 日常
python3 scripts/lint.py      # 体检（只读，不改任何文件）
git log --oneline -10        # 看最近发生了什么
git diff                     # 审阅 Agent 上次改了什么
```

## 命名约定（一句话）

页面用**中文名**，技术专有名词保留原文（`JVM 垃圾回收`、`Spring Boot 自动配置`、`Bash 数组`），英文叫法写进 frontmatter 的 `aliases`。不要中英混用，也不要同一个概念开两个页面——**一个概念只有一个规范名**。完整规则见 `AGENTS.md` §3。

## 目录一眼看懂

```
raw/            你的原始资料（Agent 只读）
wiki/concepts/  概念：为什么、是什么
wiki/howto/     操作：怎么做（含验证方式与已知坑）
wiki/entities/  工具、语言、框架、人物
wiki/sources/   每份来源一页摘要
outputs/        问答与体检的结论（★ 你的复习层，按技术栈分子目录）
wiki/index.md   总目录
wiki/log.md     操作流水账
wiki/QUESTIONS.md  你的开放性疑问
```

`concepts/` 和 `howto/` 下面按技术栈分了子目录（Java / Python / Bash / OS / 系统框架 / 通用）。同类知识聚在一起，方便集中复习。

**`outputs/` 是单独的一层，专门给你复习用**：`wiki/` 是 Agent 维护的导航层，页页互相咬合；`outputs/` 里的每一页独立成篇，讲清楚一件事，需要深挖时再点链接跳进 wiki。体检报告放在 `outputs/维护/`。

## 你的边界

| 做 | 不做 |
| --- | --- |
| 往 `raw/` 投递来源 | 修改 `raw/` 里的源文件（它是事实基准） |
| 提问、指方向、验收 | 手写 `wiki/` 页面 |
| 把自己的排障记录丢进 `raw/personal/` | 在 Obsidian 里手动大改 wiki 页面后不告诉 Agent |
| 与 Agent 商量后调整结构 | 自己动手在文件树里加新分类目录 |

手动改 wiki 页面是允许的，但要告诉 Agent 一声补进 log——否则下个会话不知道发生了什么。

## 质量取决于三件事

1. **摄入时的参与度**——只丢文件不说话，产出会很平庸
2. **来源的集中度**——同一个技术方向连着攒，wiki 才长得出形状
3. **是否定期体检**——技术知识过时快，不体检，旧结论会静默固化
