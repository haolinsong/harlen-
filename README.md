# Harlan 的第二大脑 · 使用手册

这是你的**技术知识库**（Java、Python、Bash、操作系统、系统框架为主）。它的本质不是一堆笔记，而是一套由 LLM 持续维护、会随你摄入而**越用越厚**的知识系统。

本文件是写给你（人）的完整手册：这个库长什么样、为什么这样设计、以及每天怎么用。`AGENTS.md` 是写给 Agent 的规则书，两者冲突时以 `AGENTS.md` 为准。

## 一句话理解

> 你负责**投递来源**和**提问**；Agent 负责**读懂、提炼、交叉链接、归档、记账**等全部维护工作。知识只编译一次，然后持续保持最新。

核心循环：

> 投递 → 摄入 → 讨论 → 验收 → 提问 → 落盘 → 体检 → 回到投递

## 结构全景

```
Harlan的第二大脑/
├── AGENTS.md          # Agent 的规则书（它每次开工前先读这个）
├── README.md          # ← 本文件：你的手册
├── 建库提示词.md       # 当初生成这套架构的原始提示词（留档+可复用）
├── 待落地清单.md       # 已评估但暂不落地的做法 + 触发条件
├── .agents/skills/    # 项目工作流与通用 Skill，按任务加载，随 Git 保存
├── raw/               # 第一层：原始资料（你的，Agent 只读）
│   ├── README.md
│   ├── assets/        # 图片、截图等附件
│   └── personal/      # 你自己写的：排障记录、学习笔记、方案设计
├── scripts/
│   ├── lint.py        # 体检脚本（只读，不改文件）
│   ├── test_lint.py   # 检查工具示例不会被误认成知识页面
│   ├── skill-sources.json # 外部 Skill 来源、固定提交和适配记录
│   └── package.json  # Defuddle 依赖；package-lock.json 锁定依赖树
├── code/              # 配套实验项目：把知识变成可运行代码
├── wiki/              # 第二层：知识网络（Agent 维护的导航层）
│   ├── index.md       # 总目录：有什么页面
│   ├── log.md         # 操作流水账（只追加）
│   ├── overview.md    # 全局综述：所有来源合起来说明了什么
│   ├── QUESTIONS.md   # 开放问题队列
│   ├── sources/       # 每份原始资料一页摘要
│   ├── concepts/      # 概念页（为什么、是什么），按技术栈分子目录
│   ├── howto/         # 操作页（怎么做），按技术栈分子目录
│   └── entities/      # 实体页：工具、语言、框架、机构、人物
└── outputs/           # 第三层：问答与体检的结论（你的复习层），按技术栈分子目录
```

`code/` 不算第四层，它是配套实验区。每个项目应自带运行说明和构建配置，方便把学习文档里的步骤真正跑通；当前包括 `code/rabbitmq-demo/` 和 `code/python-learning-demos/`。

`concepts/`、`howto/`、`outputs/` 共享同一套技术栈子目录：`Java / Python / Bash / OS / 系统框架 / 通用 / 知识管理`（`outputs/` 另有 `维护/` 放体检报告）。遇到新的技术栈，Agent 会自己建目录，不用问你。

## 三个层，各司其职

整个库分三层内容，外加一份配置：

| 层 | 位置 | 谁拥有 | 干什么 | 你什么时候看它 |
| --- | --- | --- | --- | --- |
| Raw sources | `raw/` | 你 | 原始材料，**事实来源，永不可变** | 投递时 |
| The wiki | `wiki/` | Agent | 被提炼、链接起来的知识网络 | 想查原理、追出处时 |
| Outputs | `outputs/` | Agent 写、你读 | 问答与审计的结论 | **复习、学习时** |
| The schema | `AGENTS.md` | 共同 | 规则与流程，横跨上面三层 | 想知道"为什么这么约定"时 |

一句话记忆：**raw 是你喂进去的，wiki 是它织出来的网，outputs 是你读的成品，AGENTS.md 是游戏规则。**

`wiki/` 和 `outputs/` 分开是关键设计：wiki 里的页面互相咬合、服务于导航和沉淀；outputs 里的每一页独立成篇、讲清楚一件事。混在一起，导航层和复习层会互相拖累。

## 五类页面，各写什么

| 类型 | 位置 | 回答 | 典型开头 |
| --- | --- | --- | --- |
| 概念页 | `wiki/concepts/<技术栈>/` | 为什么、是什么 | 一句定义，然后是「核心要点 / 与相邻概念的区别」 |
| 操作页 | `wiki/howto/<技术栈>/` | 怎么做 | 「适用环境 → 目标 → 步骤 → 验证 → 已知坑」 |
| 实体页 | `wiki/entities/` | 它是什么东西 | 工具、语言、框架、人物、机构的档案 |
| 来源页 | `wiki/sources/` | 这份材料讲了什么 | 出处、核心论点、关键细节、局限 |
| 输出页 | `outputs/<技术栈>/` | 这件事我搞懂了吗 | 直接给结论，深挖时点链接跳进 wiki |

**概念页和操作页的分工**：前者沉淀"原理"，后者沉淀"可复制的做法"。同样一段知识，原理进 concept，命令进 howto，两个页面互相链接。

**输出页的定位**：它是你的主题学习材料，不是知识网络的节点，也不是一次问答一篇的快照。它负责围绕一个稳定主题持续“讲清楚”，wiki 负责沉淀颗粒更细的知识与来源关系。复习时从输出页进入，需要深挖再点 `[[链接]]` 跳回 wiki。

## 归类与命名规则

**两级归类**：`concepts/`、`howto/` 下，一级按知识类型、二级按技术栈；`outputs/` 只按技术栈。同类知识天然聚在一起，方便集中复习。

**输出页按主题命名，不按日期命名**：例如 `RabbitMQ入门实战.md`。后续再问 RabbitMQ 时，Agent 会先更新这篇已有主题页；日期只记录在 `created`、`updated`、Git 和 log 中。只有体检报告、阶段审计等时间型维护产物保留日期前缀。

**一次提问不等于一个文件**：同一问题涉及 RabbitMQ 与 Maven 时，可以分别更新 `RabbitMQ入门实战.md` 和 `Maven-Wrapper.md`；不会再创建“RabbitMQ 与 Maven”式拼盘笔记。相反，同一主题隔天继续追问，也只更新原来的那一页。

**命名铁律：一个概念只能有一个名字。** 规范名用中文，技术专有名词保留原文：

- `JVM 垃圾回收`、`Spring Boot 自动配置`、`Bash 数组`、`epoll 与 select`
- 英文叫法、简称、变体全部写进 frontmatter 的 `aliases`，不单独开页
- 不许中英混用，也不许同一个概念开两个页面

**时效**：默认 90 天复核（技术知识迭代快）。真正稳定不变的原理页可手动标 `medium`（180 天）或 `low`（365 天）。

**环境标注**：你记录的多是通用原理，所以不强制写环境；但操作页涉及版本差异时，`env` 字段必须写（如 `JDK 21 / Ubuntu 24.04`）。

## 日常怎么用

在 `Harlan的第二大脑` 本地项目中发起任务，直接说明你要做什么。Agent 会依据 `AGENTS.md` 按需读取对应 Skill；不需要每次粘贴完整规则或手动调用全部 Skill。已有会话若收到规则变化提醒，回复“重新加载项目规则”，再继续当前任务。

按下面的场景选择入口，不必每次从投递到体检走完整套步骤：

| 你想做什么      | 可以直接说              | 使用的流程                                                                    | 结果                           |
| ---------- | ------------------ | ------------------------------------------------------------------------ | ---------------------------- |
| 把资料编入知识网络  | “摄入这份资料，重点关注……”    | [harlan-wiki-ingest](.agents/skills/harlan-wiki-ingest/SKILL.md)         | 更新 wiki 中的来源、概念、实体及必要的操作页    |
| 把资料整理成复习笔记 | “整理到笔记中：……”        | 同一摄入 Skill                                                               | 更新 wiki，并整合进 outputs 中的稳定主题页 |
| 提问、对比、继续学习 | “问：……”“继续补充这篇笔记……” | [harlan-wiki-query](.agents/skills/harlan-wiki-query/SKILL.md)           | 回答并给出处，将有价值的新结论并入已有主题        |
| 先记下一个问题    | “我想搞清楚……，先记录，暂不解答” | AGENTS.md 的 Add-question 规则                                              | 登记到 wiki/QUESTIONS.md        |
| 检查知识库或维护规则 | “体检一下”“请调整这条规则……”  | [harlan-wiki-governance](.agents/skills/harlan-wiki-governance/SKILL.md) | 体检报告，或指定范围的规则/文档修改           |

### 准备资料：文件、网页或直接粘贴

| 资料形式 | 你怎么提供 | Agent 怎么处理 |
| --- | --- | --- |
| 外部文章、官方文档、PDF、报错原文 | 由你放入 `raw/`，给出文件路径；网页也可用 Web Clipper 剪藏 | 只读原始文件；PDF 按需使用环境已有的 PDF Skill |
| 自己的排障记录、学习笔记、方案设计 | 由你放入 `raw/personal/`，或粘贴时说明是个人记录 | 提炼个人经验，与外部来源结论分开 |
| 图片、截图 | 由你放入 `raw/assets/` 并指明相关文件 | 结合文字，单独查看图片内容 |
| 公开网页 | 直接给出 URL，并说明摄入或整理要求 | 按需使用 `defuddle` 提取正文，再检查是否遗漏代码、表格和图片说明 |
| 一段文本 | 直接粘贴并说明出处、是否为个人记录及整理目标 | 根据已有出处编入知识库，不编造 raw 文件路径 |

你可以直接提供网址，不必先手工保存文件。网页清洗结果只进入临时目录或标准输出，Agent 不向 `raw/` 写入文件；想保留原始剪藏时，由你保存到 `raw/`。登录页、动态页面或清洗不完整的页面，需要借助可用的网页/浏览器工具补读；Markdown 原文直接读取。

仅把文件放进 `raw/` 不会自动触发摄入，还需要发出任务。

### 摄入：把资料编入知识网络

例如：

```text
摄入我提供的这份资料，先告诉我主要观点和适合补充到哪些已有页面。
```

Agent 会读完整资料，汇报 3–7 条要点，并与你确认重点和取舍。如果你已经说清重点，或明确要求批量、少监督处理，就按已有授权继续，不为同一决定反复确认。例如：

```text
摄入我提供的三篇资料，重点关注实际使用方法和适用限制。
按这个重点批量处理；有结论冲突时标出来。
```

确认后，Agent 先检查已有页面的文件名、title、aliases 和正文标题，再更新来源摘要、概念及实体；包含可复用命令或步骤时补充 howto，并说明验证方法。最后更新索引与日志；只有全局判断发生变化时才更新 overview。

个人记录不另写客观来源摘要，结论直接进入概念或操作页，标注“个人经验”，也不计入置信度的外部来源数量。

### 整理到笔记：同时获得复习材料

如果希望资料同时变成可反复阅读的学习笔记，可以说：

```text
整理到笔记中：我提供的这份资料。
优先补充已有主题页，重点讲清原理、适用场景和具体用法。
```

这仍然使用 `harlan-wiki-ingest`，在更新 wiki 的基础上，再更新 `outputs/<技术栈>/` 的主题复习页。内容覆盖“一句话结论、核心要点、怎么用、相关”，并保留已有主题中合适的结构。

仅说“摄入”或没有明确复习要求的“整理”，按普通摄入处理，主要产出在 wiki；说“整理到笔记中”“整理成复习笔记”“存成笔记”，才明确要求额外更新复习页。同一主题持续更新原页，不按日期重复创建笔记。

### 提问与继续学习：默认沉淀新结论

例如：

```text
问：Docker 的 COPY 和 Bind Mount 有什么区别？
结合现有笔记解释，并把新增结论补充到对应主题页。
```

`harlan-wiki-query` 会先从 index 找到相关页面，再读取需要的内容；信息不足时说明缺口，必要时核查外部一手来源。有价值的新结论整合进已有输出页，产生可复用的原理或操作纠正时同步修订 wiki。已有答案完全覆盖时，不为了记账制造空改。

只想先讨论时，明确说：

```text
这次只讨论，不写入知识库：……
```

本次就不修改笔记、索引、日志或问题队列。之后决定保留时，再提出“把刚才讨论的结论整理到笔记中”。

### 记录待解决问题

例如：

```text
我想搞清楚 Kafka 的消息顺序保证，先记录到问题队列，暂不解答。
```

Agent 将问题加入 `wiki/QUESTIONS.md` 的“待解决”，注明日期并记日志。后续摄入若发现资料能够回答它，会先提示你；确认后执行问答、落盘结论，再把问题移至“已解决”并附结论页链接。

### 体检与规则维护

需要检查知识库时说：

```text
体检一下，检查命名、重复页面、链接和索引，再给出具体修改建议。
```

`harlan-wiki-governance` 先运行 `python3 scripts/lint.py`，再补充语义检查；报告写入 `outputs/维护/YYYY-MM-DD-体检.md`，并登记索引、追加日志。体检给出诊断与建议，不自动扩大为批量重命名、合并或删除页面。

需要实际修改时，可以明确范围：

```text
请更新 README 中的日常使用说明，使它与现有 Skill 保持一致。
```

Agent 按请求修改并验证。若请求涉及规则或 Skill 流程本身的变化，会同步根 Schema 版本、使用手册和日志；大规模迁移及删页仍按项目约定取得授权。普通改动后的 lint 是收尾检查，不会因此再生成一份体检报告。

### 复习与查看结果

复习从 `outputs/` 的主题页进入，深挖原理时沿链接阅读 wiki。继续追问时可以指明现有文件和章节，让 Agent 聚焦补充。

完成有写入的任务后，查看 Agent 回报的修改文件、结论出处、验证结果与未验证部分，也可以用 `git diff` 审阅实际改动。已生成命令或操作页，不代表命令已在你的环境运行成功，应以实际验证说明为准。

`obsidian-markdown` 只在需要处理链接、属性、callout 等特殊语法时按需使用，通常无需单独指定。Skill 的安装、依赖恢复及显式调用方式见[项目 Skill 与按需加载](#项目-skill-与按需加载)。

## 为新主题开独立会话

RabbitMQ、Kafka、Python、Docker 这类会持续追问的主题，适合在同一个本地项目下分别开会话。以后你只要在当前治理会话说「我要开一个 X 学习会话」，Agent 必须为你生成一段可直接复制的启动提示词。

你仍需要从 `Harlan的第二大脑` 这个本地项目里创建新会话，然后粘贴提示词。这样新会话会自动发现项目根目录的 `AGENTS.md`；提示词只需补充该主题的范围和首次任务，不需要复制整套知识库规则。

> [!info] 为什么不能在空白新会话中自动提醒
> 会话只能在收到第一条消息后开始工作，也不会继承另一个会话的对话历史。因此「在你准备开会话时生成启动提示词」是可靠的交接点。

### 多会话同时工作时

同一 Local 项目中的会话不共享对话历史，但会共享同一份文件。为了避免一个会话覆盖另一个会话的工作：

- 每个会话开工时先记录 `git status --short`，把已有改动当成其他会话或你的工作。
- 学习会话只改自己的主题文件；同一页面不让两个会话同时编辑。
- `wiki/index.md`、`wiki/log.md`、`wiki/QUESTIONS.md` 和 `wiki/overview.md` 最后再更新，且写入前重新读取最新内容。
- 默认只暂存和提交本会话的文件；只有你明确说「提交全部变更」时才可以整体提交。
- 需要大量并行修改时，使用 Git Worktree 隔离各会话，再通过提交、合并或 Handoff 交接。

#### 当项目规则在其他会话中更新

每个会话开工时会记录 `AGENTS.md` 的 SHA-256，并在每次写文件前重新比较。这项检查不依赖 `git status`，因此即使另一个会话已提交规则变更，也能通过哈希发现。如果哈希改变，Agent 应暂停写入并提醒你回复：

> **重新加载项目规则**

这是本知识库约定的自然语言指令，不是 Codex 内置的 `/reload` 命令。收到后，Agent 会完整重读 `AGENTS.md`、列出影响当前任务的规则变化、复核已做工作，然后再继续。如果规则本就是当前会话按你的要求修改的，它会直接重读并更新基线，不反过来再要求你输入重载指令。若仍然出现旧规则行为，重新打开会话是最稳妥的刷新方式。

详细操作流程现在位于项目 Skill 中。修改这些流程时也会递增 `AGENTS.md` 的 Schema 版本，因此其他会话原有的根文件哈希检查仍能发现变化。重载时还会重读当前任务对应的 Skill 和必要参考。

## 项目 Skill 与按需加载

根 `AGENTS.md` 保存核心规则和工作流入口，详细步骤存放在 `.agents/skills/`，避免每个任务都加载全部操作手册。日常仍然直接说“摄入”“问”“整理到笔记中”“体检一下”，Agent 根据任务读取对应 Skill。它们不共享其他会话的聊天历史。

| Skill | 使用时机 |
| --- | --- |
| `harlan-wiki-ingest` | 摄入外部材料、个人记录，或整理主题复习笔记 |
| `harlan-wiki-query` | 从 index 查找知识、回答问题并补充已有主题 |
| `harlan-wiki-governance` | 体检、调整规则和脚本、生成新主题启动提示词 |
| `obsidian-markdown` | 处理 Obsidian 链接、属性、callout 等特殊格式 |
| `defuddle` | 清洗普通公开网页，减少导航和广告进入上下文 |

五个 Skill 都是项目级文件，随仓库迁移；PDF 继续使用当前 Codex 环境已有的能力，不重复安装。通用 Skill 仅辅助语法和工具操作，库的命名、字段、删除权限等以 `AGENTS.md` 为准。

新安装的 Skill 可从下一轮使用。Codex 会发现仓库中的 `.agents/skills/`；若选择器暂未出现，重新打开项目任务。即便客户端未自动列出，Agent 也可根据 `AGENTS.md` 的链接直接读取文件执行。旧会话发送“重新加载项目规则”即可刷新根规则及本次所需流程。[官方说明](https://learn.chatgpt.com/docs/build-skills)

需要明确指定时，可以说：

```text
请使用 harlan-wiki-ingest，把这份材料整理成复习笔记。
请使用 harlan-wiki-query，回答我的问题并补充已有主题页。
请使用 harlan-wiki-governance，检查知识库的命名和链接。
```

Defuddle 的运行依赖安装在 `scripts/node_modules/`，已被 Git 忽略。新机器克隆仓库后，在库根执行以下命令恢复；需要 Node.js/npm 和网络：

```bash
npm ci --prefix scripts --ignore-scripts --no-audit --no-fund
scripts/node_modules/.bin/defuddle --version
```

清洗结果先留在标准输出或临时目录，Agent 不写入 `raw/`。清洗失败或漏掉代码、表格、图片说明时，补读原页面。上游 Skill 已固定提交并保留许可证，本地适配记录在 `scripts/skill-sources.json`；升级时审阅差异，保留本库适配。

## 几条必须知道的约定

1. **`raw/` 只读**。Agent 绝不修改、重命名、删除里面的东西——它是事实基准。
2. **推测必须标注**。没有来源支撑的判断，Agent 会写成 `> [!info] 推测`，不会冒充事实；你的个人判断会标 `> [!info] 个人经验`，和外部结论分开。
3. **冲突要显式记录**。新来源推翻旧结论时，用 `> [!warning] 冲突` 写清双方出处，而不是悄悄覆盖。
4. **有价值的新结论落盘**。默认整合进 `outputs/` 的稳定主题页；你明确要求“只讨论，不写入知识库”时不写文件，已有答案无变化时不制造空改。
5. **置信度**：1 个来源→low，3+→medium，5+ 且无重大矛盾→候选 high（**必须你确认**）。
6. **流程图统一用 Mermaid，并且必须配文字说明**。步骤流程、状态流转、调用链和数据流等图示都写成 `mermaid` 代码块；每张图下方紧跟详细解释，说明关键节点、流转顺序、分支条件和最终输出，不允许只画图不解释。
7. **连续的新名词解释放在同一个框里**。同一段内容紧挨着解释几个术语时，只显示一个“新名词”框，在框内分别标出名称和含义；相隔其他正文或属于不同主题的解释各自保留。

## 你的边界

| 做 | 不做 |
| --- | --- |
| 往 `raw/` 投递来源 | 修改 `raw/` 里的源文件 |
| 提问、指方向、验收 | 手写 `wiki/` 页面 |
| 把自己的记录丢进 `raw/personal/` | 手动大改 wiki 页面后不告诉 Agent |
| 与 Agent 商量后调整结构 | 自己在文件树里加新分类目录 |

手动改 wiki 是允许的，但要告诉 Agent 补进 log，否则下个会话不知道发生了什么。

## 常见问题

**为什么我在 Obsidian 里看不到 `scripts/lint.py`？**
Obsidian 只显示 markdown 笔记和已知附件，`.py` 默认被隐藏。想看到它，去「设置 → 文件与链接 → 打开 Detect all file extensions」。但它本就不该在 Obsidian 里点开——请在终端跑 `python3 scripts/lint.py`。

**为什么我往 `raw/` 放了文件，wiki 没反应？**
投递和摄入是两个动作。没有代码在监听文件夹，你不说「摄入」，Agent 不动。

**为什么我的文章要单独放 `raw/personal/`？**
因为它不是"来源"，是"你的立场"。分开存放、分开标注、不计入来源数量，是防止"用自己的文章给自己背书"。

**页面用中文还是英文？**
中文主名 + 英文 `aliases`。技术专有名词保留原文。理由和"何时该整体迁成英文 slug"见 `AGENTS.md` §3 和 `待落地清单.md`。

## 它是怎么长出来的

这个库的起点是 Andrej Karpathy 的一份构想文件（"用 LLM 把 raw 素材持续编译成可维护的 wiki"），本库是它的一次实例化。搭建用的原始提示词在 `建库提示词.md`，想给别的领域复刻一套可以直接拿去改。

之后又摄入了三份方法论来源（graphify 图谱化路线、飞书上的完整搭建规格），从它们身上吸收了三样东西并落了地：**把 outputs 独立成第三层**、**用别名做跨语言去重**、**让个人写作不参与自证**。这些取舍的完整对照在 `wiki/concepts/知识管理/` 下。

页面正文骨架已经随项目 Skill 按需提供。其余评估过但条件未到的做法（来源哈希、二阶合成、英文 slug 迁移、检索升级……），连同触发条件，都在 `待落地清单.md` 中。
