# 全局综述

这一页反映「到目前为止，**所有来源加在一起**说明了什么」。每次 ingest 后检查是否需要重写，而不是简单追加。

## 一句话现状

库刚完成主题转向：从"关于知识管理方法的库"转为 **Harlan 的 IT 技术知识库**（Java、Python、Bash、操作系统、系统框架）。

目前 3 份来源**全部是方法论来源**——它们是这个库怎么运作的蓝本，不是这个库的内容主体。**技术内容仍是零。**

## 核心主题

_待积累：连续摄入 3 篇以上同技术方向的来源后，在此归纳主线。_

预期的主线方向：语言运行时与内存模型、并发与异步、系统调用与 IO、构建与依赖管理、部署与可观测性。具体以实际投递的来源为准。

## 已确认的结论

### 关于本库的方法论（来自 3 份方法论来源）

- LLM 在知识库场景中的主要价值来自**降低维护成本**，而不是更强的检索能力。
- 知识库的中间层形态不止一种：**markdown wiki 与知识图谱是互补的**——前者擅长综合与叙事，后者擅长定位与关系。
- 对**代码类语料**，"让 LLM 阅读"并非最优解：AST 能零成本、零幻觉地抽出结构。
- 让知识库不腐坏的关键不是更多内容，而是**几条可执行的流程护栏**：来源哈希、置信度分级、时效衰减、反证检验。
- **"个人写作不计入来源数量"**是防止知识库自证的关键设计。

## 争议与冲突

- **LLM 维护 vs 算法维护**：前者主张核心劳动交给 LLM，后者主张能用确定性算法的就不用 LLM。判定为互补而非替代，冲突集中在代码类语料。
- **页面命名**：本库已定案用中文主名 + 英文 `aliases`（理由见 `AGENTS.md` §3）。

## 知识缺口

**最大的缺口：没有技术内容。** 三份来源全是二手的方法论材料，按飞书那份规格自己的 lint 标准，整个库都在"覆盖明显稀薄"的警告范围内。下一步应该投递真实的技术来源，而不是继续完善结构。

其他缺口：

- 本库**没有记录"外部核实"的机制**：`sources` 字段只装 raw 文件路径，当结论来自 web 查证时无处安放（目前写在正文里）。
- [[graphify]] 的**项目本身已核实**（仓库、许可证、活跃度），但能力描述仍是二手转述，缺一次实测。
- Karpathy 关于"HTML 比 markdown 更适合高密度信息"的说法**仍未找到出处**。
- 社区反复提出但无人解决的三个问题：如何让 wiki 供外部智能体调用、qmd 卡死、"摄入当天能答对、第二天查不到"的通用解。

### 已关闭的待验证项（2026-09-17 外部核实）

- **Obsidian 的 `aliases` 可以作为 wikilink 目标**——官方帮助文档有 "Link to a note using an alias" 一节。命名规则成立。附带修正：官方禁用字符集含 `# | ^ : %% [[ ]]`，已补进 `AGENTS.md`。
- **qmd 包名确认为 `@tobilu/qmd`**（仓库 `tobi/qmd`，npm 最新 2.8.3，仍在更新）。
- **graphify 仓库确认存在**：`Graphify-Labs/graphify`，Apache-2.0，活跃。
