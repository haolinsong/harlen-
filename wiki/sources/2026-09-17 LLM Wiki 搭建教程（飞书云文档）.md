# LLM Wiki 搭建教程（飞书云文档）

**一句话摘要**：本库目前**工程化程度最高**的一份来源——把 Karpathy 的 LLM Wiki 构想展开成可直接执行的系统规格：三层模型（Raw / Wiki / Outputs）、六个操作、页面模板与 frontmatter 规范、lint 脚本、来源哈希完整性校验，以及一套防止知识库自我强化的规则。

## 它的三层模型（与本库不同）

| 层 | 内容 | 归属 |
| --- | --- | --- |
| RAW | `raw/` 下分 articles / clippings / images / pdfs / notes / **personal** | 人类所有，LLM 只读 |
| WIKI | `wiki/` 下分 sources / concepts / entities / **synthesis** / templates，加 index / log / overview / QUESTIONS | LLM 完全拥有 |
| **OUTPUT** | 查询答案、幻灯片、图表、lint 报告，写入 `wiki/outputs/` | LLM 写入，人类消费 |

关键差异：它的第三层是 **Outputs 而不是 Schema**——把"答案必须持久化"提升为架构的一层，而不是靠约定。本库则把 Schema 单列为第三层。

## 六个操作

| 操作 | 触发词 | 要点 |
| --- | --- | --- |
| INGEST | ingest / 摄入 | 11 步：算 SHA-256 → 与用户确认要点 → 建 source 页 → **概念名称对齐（slug + aliases 双查）** → 更新 concept/entity → 写 Evolution Log → 查 QUESTIONS → 更新 index → 记 log |
| QUERY | 直接提问 | 先定位 3–5 页 → 每个结论必须溯源到 source 页（**不允许只引用 concept**）→ 答案写入 `wiki/outputs/` → 末尾附 Confidence Notes |
| LINT | lint / 健康检查 | 跑 `scripts/lint.py`（9 项检查）→ 报告写入 outputs/ → 校验 qmd 索引 → 询问是否修复 |
| **REFLECT** | reflect / 发现规律 | 二阶合成，四阶段：Stage 0 反向检验 → Stage 1 模式扫描 → Stage 2 深度合成 → Stage 3 Gap Analysis |
| ADD-QUESTION | 我想搞清楚 | 规范化问题后追加到 `wiki/QUESTIONS.md` 开放问题队列 |
| MERGE | merge / 去重 | 页面合并，含跨语言合并专项流程；被合并页保留为 redirect 文件以防断链 |

**REFLECT 的 Stage 0 是这份文档最值得注意的设计**：在生成任何合成结论之前，先主动搜索反驳证据；若找不到反对来源，必须在 Limitations 节标注「⚠ 回音室风险：未找到反驳来源，结论可能存在确认偏差」。它把"这个知识库会不会自我强化"变成了流程里的一等公民。

## 七道防线：这套规格如何防错

| 机制 | 它防的是什么 |
| --- | --- |
| `raw_sha256` + lint 第 6 项 | 源文件被悄悄改动（⚠ SOURCE MODIFIED），触发重新摄入 |
| 概念名称对齐（slug + aliases 双查） | 同一概念因中英文差异被重复建页 |
| Evolution Log（强化 / 修正 / 新增分歧） | 只记当前状态、丢失认知变化的过程 |
| Confidence 规则（1→low；3+→medium；5+ 且无重大矛盾→**候选** high，须人工确认） | confidence: high 被自动晋升 |
| `domain_volatility` + Stale 阈值（high 90 天 / medium 180 天 / low 365 天） | 过时结论静默固化 |
| 个人写作不参与 source_count | **用自己的文章给自己背书** |
| `graph-excluded: true` | 系统文件污染 Obsidian 图谱 |

## 其他可复用的具体规格

- **Wikilink 铁律**：目标必须是英文小写连字符（✅ `[[value-investing]]`；❌ `[[价值投资]]`、❌ `[[ValueInvesting]]`、❌ `[[value_investing]]`）。中文名放 frontmatter 的 `aliases`，正文首行写「价值投资（Value Investing）」。
- **禁止 wikilink 的对象**：系统文件（index / log / overview / QUESTIONS）、lint 报告、操作名（ingest / query / reflect）；log 内部用纯文本路径。
- **五个页面模板**：source / personal-writing / concept / entity / synthesis，各自规定必需 frontmatter 与小节（concept 页含 `aliases`、`domain_volatility`、`last_reviewed`、Evolution Log；synthesis 页含 Counter-evidence 与 Confidence Notes）。
- **lint.py 的 9 项检查**：frontmatter 合法性、断链、index 一致性、Stub 页（正文 <100 字）、近重复概念名（Jaccard > 0.7）、SHA-256 完整性、Stale 页、跨语言重复、wikilink 格式。
- **qmd 用法**：`qmd add wiki/`、`qmd status`、`qmd query "<问题>" --json`、`qmd multi-get "<glob>" -l 40`。
- **标定（calibration）**：正式批量前先交互式处理 2–3 篇最典型的来源，审查输出质量并据此调整 CLAUDE.md。文档称这是 Karpathy 原文特别强调的做法。
- **搭建四步**：Step 1 Bootstrap → Step 2 标定 → Step 3 全系统 Audit（逐项核查规则是否落地）→ Step 4 配置 Web Clipper。

| Clipper 变量 | 正文与模板写 `{{data\|date:...}}`，应为 `{{date\|date:...}}` |

> [!info] 分析（本页观点）
> 这些矛盾不致命，但说明一件事：**长规格文档自己会漂移。** 同一条规则在两个章节有两个版本，靠人眼很难发现——上面六条里有两条正是评论区读者读出来的。对本库的启示是：schema 越短越可靠，一条规则最好只有一个出处。

## 与本库的关系

这是本库目前唯一给出**完整可执行规格**的来源，也是 [[2026-09-13 LLM Wiki（Karpathy）]] 相隔五个月后的"落地版本"。两者对同一模式给出了不同取舍：

| | 本库 | 这份来源 |
| --- | --- | --- |
| 第三层 | Schema（`AGENTS.md`） | Outputs（`wiki/outputs/`） |
| 操作数 | 3（Ingest / Query / Lint） | 6（+ REFLECT / ADD-QUESTION / MERGE） |
| raw 布局 | 扁平 | 按类型分区（articles / clippings / personal…） |
| 页面命名 | 中文文件名 | 强制英文 slug + aliases |
| 检索 | 只用 index.md | index.md + qmd |
| 额外护栏 | 无 | 哈希校验、置信度、时效衰减、lint 脚本 |

本库保持更简形态是当前的有意选择，但这些差异在库变大后值得重新评估——已记入 [[持久 Wiki 实践要点]] 与 `overview.md` 的知识缺口。
